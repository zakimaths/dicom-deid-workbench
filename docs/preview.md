# Browser demo

**[Open the demo](https://zakimaths.github.io/dicom-deid-workbench/)**

The demo gives visitors a way to try the workbench without installing Python. It has the same visual style, public samples, contrast controls and rectangle exercise as the local app, with a smaller set of capabilities.

## What happens in the browser

Selecting a DICOM exercise example downloads one prepared JSON asset from this site. The browser checks its pixel digest, renders the image, and lets you change contrast or replace selected sample pixels. An applied edit checks every selected and unselected pixel in memory. You can save the displayed picture as a PNG and download a separate exercise report.

The metadata rows were generated by the local tool during the site build. They show what that tool changed in the known example; no DICOM metadata is scrubbed by the public page. The exercise report identifies that distinction. The demo cannot open user files or export DICOM.

There is no upload control, API endpoint, account, analytics code, browser storage or service worker. Dropped files are refused without reading their contents. In the DICOM exercise, changing or clearing an image discards the working copy, and the copy expires after ten minutes. The separate teaching library displays published JPEGs and releases its active in-memory image when closed. GitHub still receives normal requests for the hosted page and sample assets.

## What gets published

`scripts/build_preview.py` writes an explicit set of files to `output/pages/`:

- The HTML page, two stylesheets, three JavaScript modules and favicon.
- The 50 teaching pictures, their thumbnails and the source/credit catalogue. See [the teaching library](teaching-library.md).
- Three local fonts and their licence notices.
- Two synthetic examples and six public-sample JSON assets containing pixel bytes, safe display settings and metadata action names without original values.
- `.nojekyll`, which tells GitHub Pages to serve the files directly.

No repository-wide copy is used. Python files, package environments, tests, DICOM containers, source metadata, credentials and local outputs are excluded. GitHub Actions runs Python to prepare the assets, but the deployed site is entirely static.

## Build and check it

```sh
uv sync --locked
npm ci --ignore-scripts
npx playwright install chromium firefox webkit
npm run build:preview
npm run test:preview
```

The test serves the build under a subdirectory, matching GitHub project-page URLs. It checks all 50 teaching pictures and eight exercise samples, contrast/reset, selecting and erasing pixels, PNG/report downloads, clearing, refused file drops and narrow layouts in Chromium, Firefox and WebKit. Requests must be same-site GETs; backend and external requests fail the check.

The deployment workflow builds this folder, runs these checks, and uploads only that folder. Changes to the demo must pass before deployment. GitHub Pages hosts the resulting frontend; it does not run the local processing service.

## Limits

A PNG preview is not an anonymised medical image. Manual rectangles can miss text, and recognisable anatomy remains unassessed. The six public fixtures are small software-testing examples, not a privacy benchmark. The local tool's [audit](audit-0.2.1.md) does not automatically validate the separate browser demo. Use the [local setup](../README.md#run-the-local-tool) when you need the supported DICOM workflow.

## Security review for this publication

The original demo publication produced 19 allowlisted assets; adding the teaching library brings this to 122 assets, and a repeat-build check produced identical hashes. A scan of the current source and 125 historical Git blobs found no common credential or private-key patterns. This is a limited pattern check, not proof that every possible secret or defect has been found.

The npm advisory scan returned no known vulnerabilities. The Python scan identified PYSEC-2026-1845 in the development test runner, pytest 8.4.2; it was upgraded to the advisory's fixed version, 9.0.3. The locked dependency scan is repeated in CI, so later advisories can still fail a future run. Test tools are not part of the deployed frontend.

The workflow actions are pinned to verified commit IDs. Build jobs have read-only repository access; only the deployment job receives Pages and short-lived identity-token permissions. Private vulnerability reporting is enabled on the repository.
